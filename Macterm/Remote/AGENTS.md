# Remote projects

This file loads when you work in `Macterm/Remote/`. The root `AGENTS.md` has the build, the architecture and the conventions. `Macterm/Server/AGENTS.md` has the client of a server, the `ServerEndpoint` that a host's link is, and `PaneSession`.

The remote code never names a view. It asks the user through `LoginUI` (`SSHLoginPrompts` gives it, through `SSHConnections.loginUI`): the notice of a login that waits, and the question before a server install. The parser of ssh's askpass prompts is `SSHPrompt`, which is pure.

## Remote Projects (#104)

A remote project is a project whose `path` is an scp-style `[user@]host:dir` (`ProjectPath` parses it). Each pane is a session of the host's server (v2, 0057), reached over the host's one ssh connection (below). The grammar for users is in `70-remote-projects.md` (in the docs of `macterm/website`).

- **A remote pane is a manual surface, driven by `RemotePaneDriver`.** The surface runs no process on this Mac (libghostty's manual surface, fork patch 0022): no command, no local `Last login` line. The driver is one task: it asks the pane's host what to run (`RemoteHost.attachment`: a channel, a plain shell, or the end of the pane) and runs it. `RemoteHosts` takes the host and the folder from the pane that shows the session (`RemoteHosts.pane`, set from `AppState.remotePane`), never from anything else, so only the user's own remote panes make Macterm connect to a host. A pane that restores before the app state is installed waits (`RemoteHosts.pane(for:)`). `stop` cancels the task, and every wait ends. In the unit-test host (`ZmxBypass.unitTestHost`) the surface keeps the fixed line `noRemoteClientCommand`.
- **Each pane is one channel on the host's link.** `attach` answers with the host's `RemoteServers.Link` (one connection to the host's server over the one ssh login), and the driver starts a `PaneSession` on it: `channel.open`, `attach`, output into `ghostty_surface_feed`, input, size and claim back as messages. One login serves every pane. A session never logs in by itself: a lost link ends it, and the driver tells the host. A second window's surface is a second channel to the same session.
- **One `RemoteHost` for each destination owns the host's state** (0264): one `RemoteHost.State` (idle, logging in, checking, waiting for the consent, installing, ready with its link, plain, unreachable with the time of the next try), a table of its sessions (`RemoteHost.SessionState`: lost, reconnecting, a create that runs), one backoff, and the roaming link. `Pane.isRemoteLinkLost` and `Pane.isRemoteReconnecting` are read from that table (`Pane.linkHost`), never set on the pane. A login or an install can wait minutes for the user: `attachment` waits with it (`async`), and every pane of the host waits for the same connect. A lost pane waits in `RemoteHost.nextTry`. Nothing posts a notification to a pane and nothing polls.
- **One link to the host's server for each host** (`RemoteServers.Link`), for `session.list` and `session.kill`. A pane close ends its session over it, or over a link that it opens with `login: false` and `install: false`: a close never asks for a login, and with no connection up the session stays.
- **An attach never makes a session.** A running session attaches (`channel.open`). A pane that comes back after a lost link asks to resume from its offset and keeps its screen and scrollback (`Macterm/Server/AGENTS.md`). Otherwise the screen is cleared first, because the session replays its own. A missing session is made (`session.create` over the link, in the folder, with the user's login shell and the host's environment from `HostCommands.createProbeScript`, run by `command.run`: it settles `TERM`, `COLORTERM` and `TERM_PROGRAM` on the host and resolves a `~`) only for a pane that never had a session on the host: a new pane, or one from before v2. **A pane exists only while its session exists.** A pane whose session ran there (`Pane.hostSessionDirectory`, persisted as `PaneSnapshot.hostSessionDirectory`, the shell's own OSC 7 folder at save time) and is gone (a host restart) closes (`close`), with no question and no new shell in its place. The folder counts only after the session tells the client whether it leads (`RemoteHost.sessionAttached`), so a create that failed never closes a pane. The project folder stays for a new tab. A server is never started empty in silence for a pane that expects a session (`RemoteHosts.step`). A session that the app made in the last 30 s (`Configuration.creationGrace`) counts as made, not as gone: a second window can ask before the host lists it, and a channel can drop before it starts. A folder that is not there prints a `macterm:` line and the session starts in the home folder.
- **A new remote project needs its folder on the host** (0358). The New Remote Project dialog's Add, `project create` and Create Project of a layout file in Settings → Projects (`ProjectsSettings.createProject(from:in:refusal:)`, 0366) call `RemoteHosts.checkFolder` first, and add nothing when the folder is missing or the host does not answer. The dialog (`NewRemoteProjectDialog`) is an `NSAlert` sheet, the same kind as the install question: its fields are the accessory, as wide as its row of buttons, its buttons have their own actions so it stays up during the check, and a line under the fields shows the connect or the line of `RemoteHosts.refusal`. The line takes room only while it has text, and after a refusal Add stays off until an edit (0393). Escape does nothing in the install step, so it cannot decline the server by accident. The install question of the host that it checks is its next step in the same window (`RemoteServerConsent.ask` gives it to `NewRemoteProjectDialog.checking`): the content dissolves (a `CATransition` fade) and the window moves to the frame that the alert gives it with `setFrame(_:display:animate:)`, with no animation under Reduce Motion. NSAlert has no API for a step change; the dialog changes the alert's text, buttons and accessory in place. The palette's remote items open it filled in (`NewRemoteProjectDraft`), and the check starts at once. An empty name is `ProjectPath.remoteDisplayName`, so it follows the folder. The CLI answers `not_found` and `internal`. A host that has a link checks with its server: the server runs `HostCommands.folderCheckScript` (`command.run`). Any other host checks first over the ssh connection (the login may ask), with the folder in hex, so a missing folder is told before the install question (0384). Only for a folder that is there does the host then connect as a new pane does: the server install may ask, and the connection stays for the project's panes. The script is a constant, not a bundled file, so a bundle without a file cannot refuse every host. Only its exit 0 (there) and 3 (missing) count; any other end is `unreachable`, and the log says why. An existing project whose folder goes later keeps the pane's one `macterm:` line. The debug-only `project create --skip-folder-check` lets the e2e suite add a project on a host that never answers.
- **A shell that exits ends the pane**, with no question (`AppState.handleProcessExit`, from the channel's `exit` message), and the host's server ends the exited session when it relays the `exit`. A lost link never ends the pane: the driver tells the host (`RemoteHost.lost`) and waits.
- **Input before the first attach stays for the shell.** A layout's `run:` is written through `manual_write` at the start (`initial_input`). `PaneSession` holds it (at most 1 MiB). A key in a pane that waits asks again (`RemoteHost.retry`).
  - **It waits until the shell reads input** (`PaneSession.heldInput`). The pty echoes input at once, so a line sent at the attach of a new shell showed before the login lines and the prompt, and again after them. The sign is an OSC 133 mark after the prompt (`input`, 133;B), a later mark, or a run (`PaneChannelEvent.mark`, `.status`). The session parses the marks (`events.zig`): the app has no second parser. The prompt mark (133;A) is too early: zsh owns the tty only after it.
  - A shell with no marks (a plain `sh`, a host's shell with no integration) gets the input after `PaneSession.shellStartWait` (2 s) from each attach. The input goes once. A stopped session sends none, and `takePendingInput` gives it back. Input after the attach (terminal replies, keys) does not wait: a shell can query the terminal before its first prompt.
  - **A session sends an `input` mark to a client that greets while the shell waits for input** (`Watch.current`). So a mark that came before the attach gives no wait. A host's server of an older build does not send it, and the input then waits 2 s.
- **No local shell for a remote project.** In the unit-test host, a remote pane prints one line and waits (`GhosttyTerminalNSView.noRemoteClientCommand`): never a local shell in a remote project, and never an exit.
- **No server** (the user chose Continue Without Server, or the host has no build, exit 4): each pane is a plain ssh login shell over the master (`server/host/plain.sh`, `HostCommands.Scripts.plainCommand`) that the app runs on a pty of its own and feeds into the surface (`PlainShell`), with no line from Macterm in the pane: the sidebar's project row shows a mark (`RemoteHosts.plainDestinations`) whose help says the host has no server and the shells stop with the connection. A folder that is not there gives one `macterm: cannot cd to <folder>` line (the host's own `cd` error goes to `/dev/null`). It has no persistence, no pushed foreground and no dot. ssh's exit 255 is a lost connection. The decline is kept (`Preferences.remoteServerDeclines`, `RemoteHosts.declined`), so the next panes do not ask; **Install Server on Host…** in the row menu of Settings → Projects shows only then, and asks again.
  - **A close asks the host if the shell is idle** (0494, Ethan: C). libghostty reads a plain pane as busy when its cursor is not at an OSC 133 prompt mark, and a host's shell with no integration sends none. So `plain.sh` writes the pid of its shell first, in an OSC that `PlainShell` removes (`PlainShellAnnouncement`). Before a pane, tab or project close or a bulk removal, `AppState.judgeClose` asks each host over the connection that is up, with no login (`RemoteHost.plainShellIsIdle`, `HostCommands.shellIsIdle`). The shell is idle when it is a shell of `/etc/shells`, sleeps, holds the foreground group, and has no child in it. An idle shell closes with no warning. A busy shell, no clear answer (BusyBox `ps`), or no answer in `AppState.plainShellAnswerTimeout` (in total) warns. A builtin that waits (`read`) reads as idle.
  - The CLI's `busy` refusal, the Close Tab intent and the quit rows do not ask: they keep the surface's reading.
- **A line of Macterm's starts on a line of its own, and the next attach or new session clears it** (`RemotePaneDriver.paneText`): a folder that is not there. A failed connect writes no line: the pane shows its badge (see below). These lines stay English, as all text that Macterm writes into a pane.
- When you quit, the channels end and the sessions stay. When you start Macterm again, each pane attaches to its session by the `sessionName` that Macterm persisted.
- v1 zmx sessions on a host keep running: nothing ends one. The remote owner-stamp reaper of v1 is gone with them.

These rules for the pane scripts come from tests against a real host:

- **Depend only on inputs that Macterm controls**. Never source `/etc/profile` or `~/.profile`, in any form. A `~/.profile` that ends in `exec zsh` took over the pane in three different ways. The environment of the user takes effect inside the session, where their login shell starts in the normal way. `remote_scripts_never_source_profiles` enforces this.
- **Host data is an argument, never shell text.** A `command.run` script (`HostCommands.createProbeScript`, `gitProbeScript`) is a constant that gets the folder as `$1` (`createProbeArgv`, `gitProbeArgv`) and expands a `~` itself (`HostCommands.expandTilde`, the same text as in `plain.sh`). `HostCommandsTests` sends folders with quotes, `$(…)` and `;` through `sh -c`, and the plain shell through `sh -c` and `csh -c`, and checks the folder that each reaches.
- The probe script runs as `argv` of `command.run`, never through the login shell of the user. It names no binary of the server. A folder that is not there gives the home folder and a `macterm:` line in the pane.
- **The host settles TERM, and the script never touches a TERM that resolves**. This includes a TERM that the user pinned to a simpler value with `SetEnv`. The probe replaces only a TERM that does not resolve, and a `dumb` or empty one (a shell may set `dumb` with no export, and the server has no ssh pty to take it from). It uses `xterm-ghostty` if the host has it. If not, it uses `xterm-256color`. The result goes into the new session's environment.
  - The probe exports `COLORTERM=truecolor`, `TERM_PROGRAM=ghostty` and the `TERM_PROGRAM_VERSION` of libghostty itself, and the session gets them. Programs depend on these variables. Claude Code sends OSC 9;4 progress (the status dot of an agent) only to Ghostty 1.2.0 or later.
- `RemoteTerminfo` installs our bundled `xterm-ghostty` entry (`infocmp -x`, then `tic -x -o ~/.terminfo -` on the host through its server's `command.run`, then `infocmp` checks the entry, as the `+ssh` of ghostty does). It starts when the host's link is ready (`RemoteHosts.Configuration.linkReady`), off the critical path, and runs over that link. If that link ends first, the install fails, and the next launch tries again. It depends on the own ghostty flag `ssh-terminfo` of the user (off by default upstream). It never caches to disk. It logs stderr only on a failure.

**Dropped connections heal by themselves (#281).**

- **A host link pings its server every 3 s and closes at the first ping that fails or takes over 3 s** (`LinkHeartbeat`, `RemoteServers.Link.watch`). A killed master can leave the ssh client alive and silent, so no read ends: only the ping shows it, and the panes show the badge with no key typed.
- **A pane survives a lost connection.** Its channel ends with no exit, and the host's link gives `PaneSession` no next connection, or its plain ssh exits 255. The driver tells the host (`RemoteHost.lost`). The pane keeps its last screen as it is: no dim, no blur (`Pane.isRemoteLinkLost`). Its cursor is faint and does not blink: the surface takes a config with the disabled cursor (`MactermConfig.disabledCursorBody`; `GhosttyTerminalNSView.isCursorDisabled`), so it differs from the hollow block of an unfocused pane. The cursor and the badge are the only signs in the pane.
- **The sidebar row shows a host that Macterm cannot reach.** The row of a remote project shows `network`. It shows `network.slash` while a pane of the project is lost (`Workspace.hasLostRemoteLink`), or while the host's roaming link is quiet (`RemoteHosts.quietDestinations`). The slashed mark has the failure color, but on a selected row of a focused list (`backgroundProminence` is `.increased`) it has the primary style and a bold weight, because red is hard to see on the accent color. The no-server mark stays beside it: a host stays plain until a link to its server is ready (`RemoteHosts.plainDestinations`).
- **One badge shows the state** (`StatusPill` in the badge row; a click does nothing). It says `Reconnecting`, with a spinner, while a try runs (`Pane.isRemoteReconnecting`), and `Connection Lost` when no try runs. It goes when the session attaches. A pane that came back after a restart (its `Pane.hostSessionDirectory` is set) also says `Reconnecting` when its first connect takes more than 3 s (`RemotePaneDriver.slowConnectAfter`, `RemoteHost.firstConnectIsSlow`). A host whose server does not answer holds that connect until the handshake gives up. A new pane shows no badge while it connects, because its login can wait for the user. A host whose link is ready marks no pane: a second window can show the pane live. It is the same for every reason: no network, a host that does not answer or refuses, a login that needs an answer, a changed host key, no server, a Windows host. Macterm writes no line into the pane for a lost link or a failed connect. The reason goes to the log.
- **Keys typed while the pane is lost are dropped**, by decision (Ethan, 2026-11-16, option C): they were typed at a stale screen. A key still starts a try at once. A Read-Only pane is the exception: libghostty sends no key of it to the pane, so a key starts nothing, and the pane waits for the sweep. A key that the running session cannot send (`PaneSessionHost.paneInputUndelivered`) marks the link lost and starts a try. Keys typed after the link died and before the ping finds it are lost too. Only keys before the first attach (a layout's `run:`, keys during the first connect) wait for the session.
- **A lost pane connects again by itself.** The sweep (`AppState.reconnectDroppedRemotePanes` → `RemoteHosts.reconnect` → `RemoteHost.reconnect`, which wakes every lost pane of the host, in any project) runs on the triggers (wake, a network change from `NWPathMonitor`, activation, project selection, a pane that became lost: `.remoteLinkDidStop`), and again every 5 s while the active project has a lost pane and the app is active (`reconnectRetryInterval`). The sweep picks the hosts of the active project's lost panes. **One backoff for each host** (`RemoteReconnectPolicy`, 0, 5, 20, then 60 s): the failure is the host's, so N lost panes of one host make one streak. A host whose try runs is skipped. After a failed try, the wait starts at the end of the try (`RemoteReconnectPolicy.tryFailed`): a try to a host whose server does not answer lasts until the handshake gives up (15 s after the login, not measured in the app), and the pane must show `Connection Lost` between tries. A failed first connect counts as a try, so the sweep waits 5 s after it. A key is not a sweep: it wakes every view of its pane at once (`RemoteHost.retry`), past the backoff. A host that can never answer (a refused key, a declined server) is tried once a minute while the app is active. **A sweep's try never asks the user anything**: its login runs in `BatchMode` with no askpass (`SSHConnections.connect(prompts: false)`), it installs nothing, and it never turns a pane into a plain shell. A key in a lost pane connects at once, and may ask for the login: the user is at the Mac. A connect that works clears the host's backoff (`RemoteReconnectPolicy.clear`), and is a trigger too (`.remoteHostDidConnect`, `ReconnectTrigger.hostConnected`): the sweep lets the other lost panes of that host attach at once with no key, under the same setting. The attach after it resumes the output, or draws the session's snapshot over a cleared screen when the session cannot resume.
- **A host that answers again clears the backoff.** When a roaming link hears its host after a gap of more than one keepalive (`LinkTransport.answersAfter`, 5 s; `.remoteHostDidAnswer`, `ReconnectTrigger.hostAnswered`), the sweep tries that host's lost panes at once (`RemoteReconnectPolicy.clear`). The gap is shorter than the quiet state (10 s), so a pane lost in a short freeze of the host heals too. It fires once for each gap, never while the host is down. One lost keepalive also fires it: the host answers then, so the try can work. A host that has no roaming link gives no such sign: its panes keep the backoff. A plain shell has no ping: its ssh finds a lost connection by its own keepalive.
- `SurfaceRegistry.makeView` passes `Pane.start` only on the first view build of a pane. A new start therefore never types a `run:` of a layout again.

## A host's server (v2, design/005 steps 3 to 5)

`RemoteServers` (`Macterm/Remote/RemoteServers.swift`) reaches the server on a host over that host's connection. It installs the server first when it is not there. `RemoteHosts` keeps one link for each host. The debug-only `macterm host server <host>` connects, and prints the server's build and the ssh commands that the connect ran.

- **Every background read of a host goes through its server** (`command.run`, `RemoteHosts.run`, 0058): Project Insights' Git state and the terminfo install. The server runs the command to its end in a process group of its own, with no pty, stdin and stderr on `/dev/null` and its own environment, and returns at most 512 KiB of stdout and the exit status. At the time limit (at most 60 s) the group gets SIGKILL and the request fails with `timeout`. `RemoteHosts.run` uses only a link that is up, or one that it opens with `login: false` and `install: false`, as a close does: a background read never asks for a login, and no ssh of its own connects to a host. A client that may create a session may run a command in one, so the method gives no new access.

- **The host scripts are files** (`server/host/attach.sh`, `install.sh`, `plain.sh`, in the bundle at `Contents/Resources/host`), so that `server/test/host_install.bats` runs the same text of `attach.sh` and `install.sh` over a real sshd on Linux and macOS. **The app sends each one as one line** (`HostCommands.oneLine`: no comment lines, the lines joined with spaces) in `sh -c '<script>' macterm <arguments>`. sshd gives that command to the user's login shell, and csh refuses a newline in single quotes. So every line of a host script ends where a join is valid (each command ends with `;`), it has no single quote, no `!` that csh reads as history, and no two backslashes in a row (fish reads them in single quotes as one). Each argument is one plain word: `plain.sh` gets its folder hex-encoded. `HostCommands.command` refuses anything else, and `RemoteServersTests` checks the bundled scripts with `sh -n` and `csh`.
- **One command checks and attaches.** `attach.sh` prints `macterm-host proxy` and execs `~/.local/share/macterm/bin/macterm-<build key> proxy`. Its stdio is one end of a socket pair. The app drops every byte up to that line (`skipToProxy`: a shell rc file of the user can write to stdout first), then `ServerConnection.handshake(fd:)` does the handshake. A current host costs this one command after the login. With no file of this build, it exits 3 and writes `macterm-host missing <system> <machine> <host id or -> <host keys>` on stderr. Exit 4 is no writable home or an OS with no build. The check writes nothing on the host. Text from the host goes into a log or an error only with its control characters removed (`HostCheck.clean`).
- **The first install asks** (`LoginUI.askToInstallServer`, which is `RemoteServerConsent` on a terminal window: Install, or Continue Without Server, which Escape presses). The answer is kept in `Preferences.remoteServerConsents`: the destination as `ssh -G` resolves it (`user@hostname:port`) → the host id and the host keys. When `ssh -G` fails, it asks and keeps nothing.
  - **The host id is a file that the first install writes** (`~/.local/share/macterm/host-id`, a UUID that the app makes), not `/etc/machine-id`: a container or a minimal host has none. An install never changes the file.
  - **The host keys are a `cksum` of `/etc/ssh/ssh_host_*_key.pub`** (type and key, sorted), so a host key change asks again. Where the files cannot be read, the value is the same for every host, and only the host id counts.
  - A host with no id file, another id or other host keys asks again. Later builds install with no question. Continue Without Server installs nothing (`Failure.declined`).
- **The install** (`install.sh`) streams the bundled gzip build for the host's `uname` (`ServerBuilds`, `Contents/Resources/server/macterm-<key>-<target>.gz`) on stdin into `bin/.macterm-<key>.<pid>.<time>`, checks the SHA-256 of the binary (`sha256sum`, else `shasum`, else the binary's own `version` must name the build), `chmod 700`, and `mv`s it to `bin/macterm-<key>`. A trap removes the temp file on exit and on a signal (a lost link). Then a symlink to the new build replaces `~/.local/bin/macterm` with the same temp-name-and-`mv` step. A file or a folder of the user there stays. The app reads each build's checksum once for each run (`gzip -dc`).
- **The newest install wins** (`ServerReplacement`, the one rule for the local and the remote server, pinned by the `replace:` hello pairs of `frames.json`; it compares `hello.build_key`, never the version text). A proxy of this build can reach a server that another build started. The app sends that server `server.exit`, once for each connect, and connects again; the sessions keep running and keep their build (design/002). It does this for a lower level, and at the same level only right after this connect installed its own build: builds of one level have no order. A server of a higher level stays: an app never downgrades a host. So two apps of one level on one host (a Debug and a Release build) share the server of the later install, and do not take turns replacing it.
- **The server removes old builds** (`pruneBuilds` in `registry.zig`): the files `macterm-<key>` in its own folder whose key no session reports, never its own, and none of the last minute (`fresh_build_ms`: an install whose proxy has not started yet). It does this when every session settled at start and after each session ends. It fails closed: only a server that runs from a `macterm-<own key>` file does it (not the Mac's bundle, not a file that an install replaced under it), and nothing while a session's build has no key. A temp file of an install is not a build.

## The roaming link (design/009, issue 0201)

A UDP link that carries a host's frames after sleep or a network change, with no login. The ssh connection stays the way in and the standby. The link is built in three parts. Only the app part changes what a user sees.

- **The packet layer is the first part** (`server/src/link/packet.zig`, `Macterm/Link/LinkPacket.swift`). It has no cipher of ours: ChaCha20-Poly1305 from the Zig standard library and CryptoKit. A packet is `key_id u32`, `counter u64` (bit 63 is the direction), the sealed payload and the 16 byte tag. The nonce is 4 zero bytes and the counter. The 12 byte header is the associated data.
- **The roam rule:** `open` says if a counter is the newest. A caller may move the peer's address only on a packet that authenticates *and* is the newest. The replay window is 64 packets. It moves only after the tag is good.
- **A packet that does not authenticate gets no reply.** The two sides must make the same bytes: the vector in `packet.zig` is checked again in `LinkPacketTests`. `zig build fuzz-link --fuzz=…` fuzzes the parser, and CI runs it (`server.yml`).
- **The host part is the second part** (`server/src/link/host.zig`, `stream.zig`, protocol level 3). `link.open {secret, key_id}` makes the server open a UDP port (first free of `MACTERM_LINK_PORTS`, default 60001-60999) and answers `{port}`. The client makes the 32 byte key and sends it in this one request, over ssh. A result and an event never hold a secret, so the host cannot send it back. `MACTERM_LINK=off` in the server's environment turns the link off (`unavailable`). `link.close {key_id}`, 60 s with no authenticated packet at the start, and 24 h of silence end a link. `link.close` works from any connection, and a full table ends the link that heard last. The end of the opening ssh connection does not end it: the link must outlive ssh, which is the case that roaming serves. A link sends nothing after 30 s of silence (`quiet_ms`) and sends again after its next authenticated packet. A key that equals another link's key is refused, because the nonce is the counter alone. The client must make a new key for each `link.open`: the host cannot see a key reused after a restart, and a reused key repeats nonces. A bad `MACTERM_LINK_PORTS` turns the link off. The socket closes with the last link. A link's client must say `hello` within 5 s, like any client. The server's hello lists the cap `udp-link`.
- **A link is an ordinary client of the server.** The host joins UDP to one end of a socket pair and the server holds the other end as a peer (`addPeer` in `peers.zig`, through `Server.pending_peers`: a request cannot add to `peers` while the loop walks it). The relay, its skip-ahead and every request work on a link as on a socket. After a roam, the same peer and the same channels go on.
- **The stream under it is go-back-N** (`stream.zig`): DATA with an offset, cumulative ACK, a window of 32 KiB, a timeout that starts at 250 ms and doubles to 2 s, a keepalive ACK every 3 s. It is not R1 of design/009 (state, not bytes): the relay's skip-ahead already sends state, so the stream stays simple. `write` takes less when 256 KiB wait, and the host stops reading the socket pair.
- **Cost control:** a packet goes to the link that its `key_id` names. A source that is not the link's current client pays one token for its AEAD check (400 tokens, 200 a second). A packet that fails gets no reply.
- **The app part is the third part** (`Macterm/Link/LinkStream.swift` and `LinkTransport.swift`, `Macterm/Remote/RoamingLink.swift`, `RemoteHosts`). `LinkTransport` is UDP seen as one connected stream socket: one end of a socket pair goes to `ServerConnection.handshake`, a thread joins the other end to UDP through `LinkStream` and `LinkPacketCodec`. Every pane channel, request and event works over it unchanged, as on the server's side. `LinkStream` is the Swift port of `stream.zig`: keep the two in step.
- **`RoamingLink.open` runs after each ssh connect** (`RemoteHost.adoptRoaming`, in the background). It needs the server's cap `udp-link` and level 3, a host name that UDP can reach (`SSHConnections.directHostname`: no `ProxyJump`, no `ProxyCommand`), and `Preferences.remoteRoamingLink` (on by default; the host turns it off with `MACTERM_LINK=off`). It makes a new 32 byte key for each link (`SecRandomCopyBytes`), sends it in `link.open` over ssh, and starts the transport. If the handshake over UDP fails in 3 s, it sends `link.close` and the host keeps its ssh link, with no message (show the exception only).
- **A link that works becomes the host's link** (`RemoteHost.State.ready`). New attaches use it. The ssh link stays as `standby` for the panes that attached over it. After sleep or a new network the ssh link dies and those panes are lost; the next attach finds the roaming link, which the host still holds, and attaches with no login. A pane that attached over the link needs no reconnect: the transport sends a keepalive every 3 s, the host learns the new address from it, and the stream resends what was lost. `RemoteHosts.networkDidChange` (the network monitor, and the wake burst) makes each transport open a new socket.
- **A link that hears nothing for 10 s is quiet** (`LinkTransport.quietAfter`, three missed keepalives). It stays, and its panes keep their channels, but the sidebar row shows the host as lost (`RemoteHosts.quietDestinations`) until a packet comes again.
- **A link that hears nothing for 5 minutes of awake time ends** (`LinkTransport.deadAfter`: the clock stops while the Mac sleeps). Its connection ends, its panes are lost, and the next connect uses ssh. A lost pane never drops a link that is still open (`RemoteHost.lost`): a lost pane on the ssh link says nothing about the roaming link, which is dropped when it does not answer a `session.list` and its transport is dead.
- **Not built:** a sign on a pane while a link is quiet (a quiet link looks frozen, as a stalled ssh does), and a Settings switch (only `remoteRoamingLink` and the host's `MACTERM_LINK=off`).

## One ssh connection for each host (v2, design/005 step 1)

`SSHConnections` (`Macterm/Remote/SSHConnections.swift`) gives each host one ssh connection. Every pane of a remote project is a channel over it (above). The debug-only `macterm host connect <host>` opens one.

- **The user's own ControlMaster first.** If `ssh -G` names a ControlPath and `ssh -O check` finds a master there, Macterm uses it and opens nothing. Otherwise it runs `ssh -M -N` with its own ControlPath, `<App Support>/cm/<hash>` (mode 0700, `SSHControlPath`). The path is a hash, because a socket path holds 104 bytes. The master gets the path with `-S`, never `-o ControlPath=`: ssh splits an `-o` value at spaces, and `Macterm Debug` has one.
- **A command over the connection never logs in by itself** (`run`, `ttyArguments`; `connect(login: false)` uses only a connection that is up): `BatchMode=yes` refuses a prompt, and `ProxyCommand=/usr/bin/false` stops the direct connection that ssh tries when the control socket does not answer. `RemoteCommand=none` is there because a `RemoteCommand` in the user's config makes ssh refuse a command line.
- **Macterm's master stays after quit, until the link drops** (issue 0084, the type's doc comment has the rules). `ControlPersist=yes` moves it into the background after the login, so only the ssh of a login that has not finished is a child of Macterm (`loggingIn`), and only its askpass gets an answer. The next launch uses a live master on its own path. The askpass variables go only to the master's own process, never to the app's environment, so a pane's ssh never gets them.
- **A changed config logs in again.** The own path is a hash of where `ssh -G` sends the host (`SSHControlPath.endpointKeys`), and each connect reads `ssh -G` again, also while Macterm runs.
- **Macterm ends its own master when the config no longer gives its path.** `<App Support>/cm/connections.json` records the path of each master that Macterm started, because the hosts of an ssh config cannot be listed. The check runs at the next connect for that host, and at launch for each record (`endStaleConnections`). A config that `ssh -G` refuses (exit 255) also ends it. A time-out does not. A master that two destinations record ends only with the last record (`release`). `ssh -O` reads no config (`-F /dev/null`), so a broken config cannot keep an old master.
- **The login asks the GUI** (`SSHLoginPrompts`): the master has `SSH_ASKPASS` set to `Contents/Resources/ssh-bridge/macterm-askpass` (`scripts/askpass-shim.sh`, which execs `macterm askpass`) and `SSH_ASKPASS_REQUIRE=force`. The askpass sends ssh's prompt to the app named in `MACTERM_ASKPASS_SOCKET` (`ssh.askpass`). The app shows an `NSAlert` sheet on a terminal window: a secure field, or Connect and Cancel for a host key or a confirmation.
- **The sheet says less than ssh** (`SSHPrompt.Question`). Macterm knows a question only by the exact text that OpenSSH writes, and shows its own text for it: a password (`bob@box's password:`, or `(bob@box) Password:` of keyboard-interactive), a key passphrase (`Enter passphrase for key '…':`), and a new host key (Macterm's sentence, then the host that ssh names, with `ProxyJump` possibly the jump host, and the key's type and fingerprint in a monospaced label, `hostKey(in:)`; OpenSSH 10.5 writes `is:` before the fingerprint). Any other question shows only ssh's last prompt line, cleaned (`promptLine`), never ssh's other text. The exception is a yes or no question that Macterm does not know: it is about the host's key, so it fails closed and shows ssh's lines above the question. A form that a later OpenSSH changes becomes unknown until a test adds it. The same secret prompt again from the same ssh (`isRetry`: the master, or a jump host's ssh under it) means that ssh refused the answer. The sheet then says that the password, the passphrase or the answer is incorrect (`Question.refusal`).
- **The sheet's field lines up with its text and buttons** (`SSHLoginPrompts.columns`). NSAlert puts an accessory at the left edge of its buttons, and its text a few points in (measured on macOS 27). The password field is as wide as the buttons, and the host key lines move in to the text.
- **A login that asks nothing shows ssh's last line** (`SSHLoginNotice`, `LoginUI.showNotice`). A host can write text and wait with no question, for example a link to log in from the browser. When the last line that ssh wrote since the last question stays the same for `SSHLoginNotice.delay` (2 s), a notice sheet shows it with Cancel, and Open Link (`NSWorkspace.open`) when the line holds an https link. The link starts its own line of the text (`noticeText`), so that it does not wrap after `https://`. The rule is the same for every host: it matches no vendor's text. ssh's own warnings (`Warning:` and `** ` lines) do not count. Open Link keeps the sheet up. A new line changes the text in place. The notices of all logins wait behind any question, and the sheet shows the first one. A notice goes away when its master listens or exits. With no terminal window, no notice shows: a modal alert would hold the wait that closes it. A quiet login (`connect(prompts: false)`, the automatic reconnect) runs in `BatchMode` with no askpass and shows no notice. Connect errors go to the log, and the pane shows its badge.
- **One Cancel ends the login** (`cancelLogin(connectionPID:)`): ssh would ask again, for the next try and then the next method. The connection fails with `Failure.cancelled`. Only the master gets the signal: a jump host's ssh under it can ask once more, gets `denied`, and exits.
- **The answer goes only to an askpass of Macterm's own ssh** (design/006 §4). `ControlSocketServer` reads the peer's pid (`LOCAL_PEERPID`). `askpassOwner(forPeer:)` requires two things. The peer runs the bundled `macterm` (a pid alone can be reused). A running master of Macterm is its parent, or an ancestor at most `askpassAncestry` steps up. ssh execs its askpass directly, and the shim execs too, so for the host's own login the parent is the master. A `ProxyJump` host's login comes from an ssh that the master starts through `sh -c`, lower down. Any other process gets `denied`.
- **A saved password fills the login only after a click** on Use Saved Password, and then `PasswordAuthenticator`. The entry is v1's: `ssh <destination>` and the prompt line.
- **Each new login writes a log line**, `ssh login: host=<host> logins=<n>`, so the logins of a day can be counted from the log (design/005, the question of a link that roams).
- A quit ends only a login that has not finished (`endLogins`). `disconnect` ends Macterm's master with `ssh -O exit`. A user's master is never ended.
