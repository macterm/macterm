# The server clients

This file loads when you work in `Macterm/Server/`. The root `AGENTS.md` has the build, the architecture and the conventions.

## The app's client of the local server (`Macterm/Server/`)

`LocalServer` and `ServerConnection` connect the app to `macterm server` (design/001 A, design/002). `LocalSessions` holds the app's one connection, and every local session path goes through it (see "Local panes are v2 sessions" below).

- **The app starts the server.** `LocalServer.connect` connects to `<runtime dir>/.server`. When nothing answers, it runs the bundled `zmx server` with `MACTERM_RUNTIME_DIR` set, so that the app and the server use one directory. `runtimeDirectory(environment:)` finds it as `resolveDir` in `server/src/runtime.zig` does.
- **A newer app replaces an older server** (`ServerReplacement`) with `server.exit`, then starts its own. The sessions keep running.
  - A lower level is older. A higher level is never replaced.
  - At the same level, another build is replaced only when it runs from this app's own `zmx` path, or from a file that an update removed. `proc_pidpath` of the socket's peer follows a bundle that moved, and gives no path after a delete (measured). A real Sparkle update is not measured yet.
  - A build from another app (Debug next to Release) stays. The order of two builds of one level is not known.
  - One `connect` replaces at most once, so two apps never replace each other's server in a loop.
- `ServerConnection` reads the socket on a thread of its own. A request waits for its response by id. `events` gives one element for each event batch. When the connection ends, each request that waits fails with `ServerClientError.disconnected`. Only the reader thread closes the fd, under the lock that each write holds.
- `LocalServerTests` runs the bundled server in a runtime directory under `/tmp` (a socket path has at most 103 bytes).

## One endpoint for local and remote sessions (F11, issue 0265)

- **`ServerEndpoint` is where a pane's session lives**: `connection()`, `list`, `kill` and `run`. `LocalSessions` is the local endpoint: it starts the server and tries for a few seconds (`LocalSessions.connection`). A host's link (`RemoteServers.Link`) is the endpoint of the panes that attach over it: it gives only its own connection, and the pane's `RemoteHost` connects again with its backoff.
- **`PaneSession` takes an endpoint and has one rule for a lost link**: a channel that ends with no exit reports `paneLinkLost`, forgets the lead and the flags, and asks the endpoint again. An endpoint with no connection to give ends the session with `paneGone`. A channel that fails or ends within 2 s counts as a failed try; after more than 12 in a row the pane is gone.
- **`PaneRoute.make` picks the pane's route** (a `PaneSession` on the local endpoint, or a `RemotePaneDriver`), so the view only hosts the surface.
- **`ServerLink` is a connection as a pane and a list use it.** `ServerConnection` is the one that the app runs. `FakeServerLink` (`MactermTests/Support/`) is an in-memory link that speaks frames, for tests with no server (`PaneSessionEndpointTests`).
- `SessionInfo` is a session as any server lists it. `ServerLink.call(_:_:timeout:)` bounds a request (`serverRequestTimeout`, 10 s).
- Not built: a state stream of the endpoint (nothing reads one yet), and resume by offset on the app's channels.

## The model shadow (design/010 §9, step 3)

`AppState` still owns the model. A Debug or tip build (`ModelShadow.isEnabled`) gives the server `MACTERM_STATE_DIR` (the App Support folder), and after each `saveWorkspaces` sends it a copy of the model in `model.replace` (`ModelShadow`, `ModelConversion`). `ModelMirror` follows the server's batches (`LocalSessions.setModelFeed`). A Debug build compares the mirror with the copy that the server took and logs a difference. Nothing reads the mirror, and a user sees nothing. A server that another build started with no state folder has no model: the shadow then sends nothing.

## Local panes are v2 sessions

Every local pane (workspace, pinned, quick terminal, widget) is a v2 session of the local server. Remote panes are v2 sessions of the host's server (see `Macterm/Remote/AGENTS.md`).

- **A local pane is a manual surface** (libghostty fork patch 0022, `manual_io`), fed by a `PaneSession` on the app's connection to the server (`LocalSessions.connection`). The app asks libghostty for the pane's launch (`ghostty_launch_resolve`, fork patch 0023: login(1) on macOS, shell integration, `TERM`, `GHOSTTY_*`, the config `env`, a palette's command wrapper), and `session.create` runs it, with the surface's folder and size. A session that exists is attached, and the launch is not run. `manual_write` (keys, pastes, terminal replies, `initial_input`) goes to the channel from a queue of its own, `manual_resize` goes as `resize`, and the claim as `claim` (`GhosttyTerminalNSView+Channel.swift`). With no bundled server, or over the socket-path budget, the pane is a plain, unpersisted shell: a normal surface.
  - `session.create` takes `env` (`NAME=value` entries). The server sets its own `MACTERM_RUNTIME_DIR` in it, so the session listens where the server looks. The surface's env pins `MACTERM_RUNTIME_DIR` to the app's runtime directory.
- **A snapshot is drawn only at the grid that it was laid out for** (`PaneSession.read`). `PaneSession` holds an attach's snapshot until its end. When the grid changed while the client leads, it drops the snapshot and the output after it, and attaches again at the new grid, at most `PaneSession.attachAgainLimit` times on one channel.
- **`LocalSessions` is the app's one server connection** (`LocalSessions.shared`). It connects at the first use and again after the connection ends (the server exits when it has no session and no client). `MactermApp` connects at launch, so a server of an older build is replaced early. `SessionClient.live` sends `killSession`, `listSessions` and `session list/info/kill` through it.
- **The app ends a session whose shell exited** (`session.kill` takes the status): at its `session.exit` event, and at each connect for one that exited while no app was connected. Its pane already closed at the channel's `exit` message. Without this, a session keeps its exit status for ever, and a pane of the same name attaches to an exited session.
- **The shell and the tty come from the channel's `state` message**: `shell_pid` (the pty's leader) and `pty` (`Pane.sessionShell`). `ProcessInspector` reads the foreground group of the shell from it, and the pty is the tty of the password monitor and secure input. The pane's name, title, folder and marks come from the channel's own messages, for local and remote panes alike.
- **A session keeps each pane's attention flags** (`Attention`: `unseen`, `failed`, `bell`, `events.zig`; design/004 §6). A run that ends and a bell set them. A new run clears `unseen` and `failed`. They live in the session process, so they stay while the app is quit and across a restart of the server: a new server reads them from the session. `session.list` shows them, and the server sends `pane.attention` to every client at each change. `pane.seen` (local clients only) tells the session to clear them, and the reply goes after the event. The session also sends the flags as an `attention` message on each pane channel, and takes `seen` there. The GUI uses the channel: each pane already has one, local or remote, so the GUI needs no table from a session id to a pane (`Pane.attention`, `PaneSession.seen`).
- **No listing gate.** One server answers every list. `session list` lists only running sessions. `clients` is the session's own count of the clients that sent `attach`: the session sends `state` again to the server each time the count changes.
- **The local orphan sweep runs once at launch** (`AppState.sweepLocalOrphans`, `ZmxReaper.localOrphans`): it ends a running `macterm-` session that no pane claims and no client shows. It is safe because each build flavor has its own runtime folder (`LocalServer.folderName`: `macterm`, `macterm-debug`), so every session there is this flavor's. This also keeps a Release pane's session off the Debug binary. It skips everything when `WorkspaceStore.loadFailed`.
- **`zmx connect <name> --` (the CLI's pty client and the benchmark's, not the app's) asks the server first, also when the socket answers.** The server refuses a create for a session whose shell exited (`exited`); the client ends it (`session.kill`) and creates again, as v1's `zmx attach` made a new session for a dead one. A connection that ends before the reply (a server that a newer app replaced) gets one more try.
- **The first v2 launch ends v1's local sessions** that the restored panes name (`AppState.endV1SessionsOnce`, design/008 §4 Q3 A), with the programs in their panes. Each pane already opened a new v2 session of the same name, with a new shell in its saved folder. v1.33.2 ships zmx 0.8.1, and `zmx kill` of 1.0.1 hangs against it, so Macterm uses no zmx IPC here (`V1Sessions`): it finds each daemon by its argv (`zmx __daemon <name>`; a v2 session is `__session`), sends SIGHUP and SIGTERM to every descendant of the daemon and every process in its pane's pty session (of the user's real uid, so setuid programs too), SIGTERM to the daemon, and SIGKILL to what a new scan finds after 2 s. Then it removes the sockets from v1's socket folder (`ZmxSocketBudget.v1SocketDir`). `Preferences.endedV1Sessions` is set only when a full scan finds no daemon of the names. Otherwise, also when a scan fails, the next launch tries again. A hermetic run (`PasswordVault.isHermetic`) neither reads nor writes the flag, because it shares the real defaults domain. v1 sessions that no pane names, and the sessions of remote projects (`localSessionNames`, also for a host that is this Mac), are left alone. Not found: a program that `setsid`'d away from its pane, and a daemon whose re-exec failed (it keeps the argv `zmx attach <name>`).
- The unit-test host starts no server and runs no session (`ZmxBypass.unitTestHost`): every live session call returns nil or does nothing there.
- The server tests are `server/test/connect_create.bats` (the create path of `zmx connect`, which is the CLI's client now) and `server_v2.bats`. The app tests are `PaneChannelTests` and `PaneSessionTests`, against the bundled server, `PaneSessionEndpointTests` on `FakeServerLink`, and `RemoteHostsTests` (`Macterm/Remote/`) on a local sshd.

## Sessions of an older build (design/002, option A)

A session keeps the build that started it. After an update, `AppState.outdatedSessions` holds the running local sessions whose build key differs from the bundled server's, and the sessions whose own file an update deleted, also with the same key (`SessionBuild`, from `session.list`'s `pid` and `ProcessInspector.executableIsDeleted`; refreshed with the zmx cache). macOS denies Documents, Desktop and Downloads to such a session and its programs. A restart from the new bundle gives the access back, and the pill's help says so. A pane whose session is in it shows an **Outdated** pill in its trailing badge row (`TerminalPane`, `AppState.showsOutdatedSessionBadge`). A click on the pill restarts that pane's session (`requestRestartSession(of:)`). **Restart Session** (`AppCommand.restartSession`, no default chord) is available only while the active tab has such a pane, and restarts all of them. A restart swaps each older pane for a new pane in the same folder, ends the old session, and asks first when a program runs (`paneNeedsConfirmClose`). Panes of one tab that show one session restart together. It never runs by itself. Not built: restarting all idle tabs (option C), keeping the old screen, and remote sessions.
