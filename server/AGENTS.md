# The session server

This file loads when you work in `server/`. The root `AGENTS.md` has the build, the architecture and the conventions.

- **The server has no pin.** `scripts/build-server.sh` builds it for macOS universal and Linux x86_64 and aarch64 (static musl, stripped). That script holds the Zig version and the flags.
  - The build key is the hash of the git objects of `server/src`, `server/build.zig`, `server/build.zig.zon`, that script and the two schemas that `macterm mcp` embeds (`assets/palette.schema.json`, `assets/project.schema.json`), from the working tree. Tests, the protocol schema and host scripts are not in it, so a change to them makes no new build. `zmx version` reports `1.0.1+thdxg.<key>` for people; `hello.build_key` and `session.list`'s `build_key` carry the key itself.
  - **One manifest describes a build**: `macterm-<key>-server.json` next to the tarballs (key, targets, SHA-256 of each tarball). Every script and workflow takes the targets from `build-server.sh targets` and checks a build with `build-server.sh verify <dir> [key]`, never on its own.
  - Setup installs the build for the key and copies its manifest to `Macterm/Resources/zmx/server.json`, last, as the stamp. It takes, in order: `build/server` (CI puts its own build there); a Zig build when the sources have changes that are not committed; the prebuilt from the `server-prebuilt` release; a Zig build.
  - `.github/workflows/server-build.yml` builds on `macos-26` with Xcode 26.3, because zig cannot link with Xcode 26.4 or later (zig#31658). Its Linux job `Find Prebuilt` takes the prebuilt when it exists, and the macOS job `Build` then does not run. It uploads a new build on `main` and on pull requests from this repository, and never replaces an asset. Every 6 hours, `server-prebuilt-prune.yml` runs `scripts/prune-server-prebuilts.sh`. It removes each build except the build of main's key, of the head of each open pull request, and of the last 14 days. It removes a build as a whole, and removes nothing when it cannot find one of those keys.
  - The release workflows build from the commit, never from a prebuilt.
  - `build.sh` refuses a bundle whose server is not the build of the tree.
  - **The app carries a gzip build for every host target** for an install on a host, with no download: `Contents/Resources/server/macterm-<key>-<target>.gz` for `universal-macos`, `x86_64-linux` and `aarch64-linux`. The app reads the build key from the name of the macOS file (`ServerBuilds.bundledKey`); `embed-zmx.sh` names the files with the key of the installed manifest. `setup.sh` makes the Linux files next to `zmx`; `embed-zmx.sh` makes the macOS file from the signed `zmx`, so it has the app's identifier. The app's signature seals all three. `build.sh` refuses a bundle without them or with a macOS file that is not the bundled `zmx`. `build.sh` and `BundledResourcesTests` also check that each Linux file is an ELF binary for its machine.
- **The server has no v1 code.** It started as the zmx fork at upstream v1.0.1 (the `DOWNSTREAM.md` of thdxg/zmx names each change by its old patch number: 0003 is the leadership claim, 0004 the disclaim, 0010 the foreground report). Its own verbs are `server`, `connect`, `proxy` and `version`, and the hidden `__session` (the session process) and `__create-session` (tests make a session with it). Every other word goes to the `macterm` CLI (see below). v1's verbs (`attach`, `list`, `kill`, `get`, `set`, `clear`, `history`, `send`, `__daemon`) and their daemon are gone. A v1 session daemon (zmx 0.8.1) keeps running until the first v2 launch ends it by its argv (`V1Sessions`). Remote panes are sessions of the host's v2 server, and v1 sessions there keep running.
- **The server is the one owner that ends a session whose shell exited** (`registry.statusRead`). It ends the session after a client read the status, and `session.create` with `replace_exited` ends it and starts a new one. `Macterm/Server/AGENTS.md` has the reads.
- **The leader's terminal answers the terminal queries.** While no client leads, the session's ghostty-vt terminal answers them (`Watch.answers_all`), except the OSC color reports and the kitty graphics replies. The session answers the OSC 7501 support query at all times. No byte scanner answers a query.

## The model (design/010, `src/model/`, `src/model_ipc.zig`)

- **Only a server with `MACTERM_STATE_DIR` has a model.** A host's server answers `state.subscribe` with no model, refuses each model request with `unavailable`, and writes no file.
- **The server writes `model.json`** 100 ms after a change, before the reply to `server.exit`, and when it stops. A file that does not read, or that a newer build wrote, makes the model read-only (`model_readonly`), and the server never writes over it.
- **One request, one batch, before the reply.** The server makes the events from a compare of the model before and after the request (`Snapshot`, `diff`). The requester's copy has `cause`. A request that fails sends no batch.
- **A pane that leaves the model ends its local session**, unless another pane of the model names the session. `pane.removed` and the reply name every pane that left. `model.import` ends no session.
- **`model.replace` is the shadow stage** (design/010 §9, step 3). The app sends its own model after each save, any number of times. It ends no session and leaves `imported_v1` false. Once the model has `imported_v1`, the server refuses it (`refused`). Step 7 removes it.
- **The ring of request ids** keeps 256 answers by client key, request id and a hash of the arguments. `state.subscribe` gives the key as `client`; `control.resume` takes it. `split.ratio` and failures for lack of memory are not kept.
- **The model and each batch must fit in one frame** (`server.frame_max`, 1 MiB).
- **The schema reads the model through `src/wire.zig`**, because a file can be in one module only.

## The macterm CLI (design/011)

The port of the Swift CLI to Zig is in `src/cli/`. The Swift CLI stays `Resources/bin/macterm` until the swap (design/011 §3). Until then, nothing that a user sees changes. To run the Zig CLI, use `zig-out/bin/zmx <verb>`.

- **The v1 contract is the test.** `golden/` holds the grammar and the output of the v1 CLI (`contract.zig`). The tests in `cli.zig` check these items:
  - each ported command against `contract.json`: abstract, usage, options, arguments and subcommands;
  - the help of each ported leaf command against its `golden/help` file, byte for byte;
  - each line of a ported verb against `cases.json`;
  - each verb against a stand-in server on a real socket: the method that the CLI sends, the output and the exit code.

  A port issue adds its verbs to `root` and sets the `method` of its lines in `cases.input.json`.
- **Exit codes**: 0 when the command worked, 1 when the server refused it or it failed, 2 when no server answered, 64 for a usage error (as ArgumentParser).
- **The CLI never starts the server.** `status` must fail while the app is not up.
- **Discovery** (`client.candidates`). These are the steps, in order:
  1. `--socket` gives one socket.
  2. If there is no `--socket`, `MACTERM_RUNTIME_DIR` gives its `.server`.
  3. If there is no `MACTERM_RUNTIME_DIR`, the CLI tries the folder of each build flavor: `macterm`, then `macterm-debug`. `LocalServer.runtimeDirectory` makes the same folders.

  The CLI does not read `MACTERM_SOCKET`, because that variable names the app's `control.sock`.
- The CLI sends `hello` with the role `cli`. A server of another build refuses it. The CLI then exits with 1 and shows the two builds. The server's pid comes from the socket (`runtime.peerPid`), not from the server.
- **The pane verbs act on one session.** `--session` names it. With no `--session`, `MACTERM_SESSION` names it, but not when `--tab` or `--pane` is given (v1's rule). `--project`, `--tab` and `--pane` name a pane in the model (design/010): until the model moves to the server, they fail with exit 1.
- **The session methods need no GUI.** `pane run` sends `session.send`, `pane key` sends `session.key`, `pane dump` sends `session.history` and `pane inspect` sends `session.inspect`. The server gives each one to the session process, which answers from its own terminal.
  - `session.send` types the text as it is, with no paste brackets, as v1 typed it. Before `--`, `pane run` refuses a word that starts with a dash (exit 64).
  - The session encodes the chord of `session.key` with the key modes of its terminal (`chord.zig`, ghostty-vt's key encoder). The grammar is the keybind grammar of the app (`HotkeyRegistry.parseShortcut`).
  - `session.history` holds at most 960 KiB, because a session's frame to the server is at most 1 MiB. Longer text keeps its end, and the CLI says so on stderr.
  - The cell size, the surface size, the content scale and read-only are the GUI's: `pane inspect` prints `-` for them, and `pane run` refuses no read-only pane yet. `session.key` treats Option as Alt, Macterm's default. The pane column of `session list` is `-` until the model.
- **The agent skills are files** in `src/cli/skills/`, and the binary embeds them (`skills.zig`). `macterm skills` needs no server. Until the swap, the Swift `AgentSkills` holds the same text, and `AgentSkillsTests` checks that the two are equal: change both together. A Zig test parses each `macterm …` line of the skills against `golden/contract.json`, and a command that exists only in Debug builds fails it.
- **`macterm api` reads the schema of its own build** (`src/protocol/metadata.zig`, the comptime metadata that `tools/schema.zig` writes as `schema/protocol.json`). `api list` and `api describe` need no server.
  - `api list` shows only the methods that a `local` client may send. Each of these methods must have a `doc`, or the build fails.
  - `api describe` prints the arguments and the result as JSON Schema. A named type is in the top-level `$defs`.
  - A field's `field_doc` is its `description`, and its `field_limits` are JSON Schema keywords (`maxLength`, `minItems`, `minimum`). Each field of the arguments and the result of a listed method must have a doc, or a test fails. A limit is only what the server checks itself: the server still refuses the request. `maxLength` counts bytes on the server and characters in JSON Schema.
  - `api call` reads the arguments as JSON with the keys of the wire. It refuses an unknown key or a bad value before it connects (exit 1), and prints the result as JSON. A `bin` is a JSON string: bytes that are not UTF-8 print as U+FFFD.
- **`macterm mcp` is an MCP server on stdio for coding agents** (design/014, `src/cli/mcp.zig`). It answers `initialize`, `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/templates/list` and `resources/read`, and nothing more. Each tool is one method: the name with `_` for `.`, the method's `doc` as the description, and the schemas of `api describe` as `inputSchema` and `outputSchema`.
  - **To make a method a tool**, give it a `doc` and a doc for each field, and add it to `tools` with its hints (read-only, destructive, idempotent). A tool that is not a `local` method with a `doc` fails the build. Then write `src/cli/golden/mcp-tools.json` again: `printf '{"jsonrpc":"2.0","id":1,"method":"tools/list"}\n' | zig-out/bin/zmx mcp | python3 -c 'import json,sys; print(json.dumps(json.load(sys.stdin)["result"], indent=2))' > src/cli/golden/mcp-tools.json`. A Zig test and `test/mcp.bats` compare `tools/list` with it.
  - Plumbing is never a tool: `command.run`, `server.exit`, `model.*`, the channel and link methods, `control.resume`, `pane.seen`. No tool may return a `secret` (a test).
  - Each call connects again, with the discovery of the CLI and the role `mcp`. The server refuses another build for `mcp` as for `cli`. With no server, a call is a tool error: "Macterm is not running. Start Macterm and try again." It never starts the server.
  - **The password rule** (design/014 §5). For the role `mcp`, the server answers `session.send` and `session.key` with `forbidden` ("The pane reads a password. Ask the user to type it.") while the pty is in canonical mode with echo off. The CLI keeps v1's behavior. The role gives no trust (design/006 §2): an `mcp` client may send what the CLI may send.
    - Before it types, the server holds the input and asks the session for its line modes now (`tty_read`, answered with `tty_mode`). Input of a client that left before the answer is not typed.
    - A session with no `tty-read` cap in its `hello` (an older build) gets no input from `mcp` ("The session runs an older build that cannot say if the pane reads a password. Ask the user to type it."): fail closed.
    - The rule blocks too much: a program that is not a password prompt can read with `ICANON` and no `ECHO`. It also blocks too little:
      - A prompt in raw mode passes (`sudo` with the pwfeedback option, a Node readline prompt, a mask that a program draws).
      - The check reads the mode at one moment. Text sent at the shell prompt ahead of a password read (`sudo true` and the password in one send, or two quick sends) waits in the line buffer, and the prompt can read it.
      - The user sees what the agent types (design/014 §5, rule 3). That is the control for these cases.
  - A fault of a call (bad arguments, an error of the server, a result larger than `result_max`) is a tool error (`isError`), so that the model can read it. An unknown tool or method is a JSON-RPC error.
  - **The resources are the file formats** (`resources`): `macterm://formats/palette` and `macterm://formats/layout`. Each one is a schema of `assets/` as the website publishes it, with an example in its `examples`. `build.zig` embeds the two files (the `formats` module), so there is no second copy. `CustomPaletteFileTests` and `ProjectFileTests` check that each example parses. The `instructions` name each resource, because a client may not list resources by itself (a Zig test).
  - `src/cli/mcp_instructions.txt` is the `instructions` of `initialize`: the rules for all tools, at most 250 words (a test). The agent shows it in each conversation, so keep it short.
- **`ssh` and `askpass` need no server** (`src/cli/ssh.zig`, `src/cli/askpass.zig`). Until the swap, the Swift `SSHWrapper` and `AskpassCommand` hold the same rules. `src/cli/fixtures/` holds the cases, and the Zig tests, `SSHWrapperTests` and `ControlProtocolTests` read them: change the two sides together.
  - `ssh` embeds the `xterm-ghostty` entry as text (`src/cli/terminfo/xterm-ghostty.terminfo`: the output of `infocmp -x xterm-ghostty` without its first line, which is a comment with a path). `SSHWrapperTests` compares it with the entry of the pinned GhosttyKit. After a pin that changes the entry, write the file again.
  - The cache key of `ssh` is the hash of that text. The Swift CLI hashes the output of `infocmp` with its comment, so after the swap each host gets the entry one more time.
  - `ssh` becomes the real ssh with `execvp`. The install's `ControlPath` has the pid in its name.
  - `askpass` sends the v1 request `ssh.askpass` to `MACTERM_ASKPASS_SOCKET`, which is the app's `control.sock`.
- **Use a streaming writer for output** (`writerStreaming`). A positional writer writes at the start of a file, also when the shell opened the file to append.

## The roaming link (design/009, issue 0201)

A UDP link that carries a host's frames after sleep or a network change, with no login. The ssh connection stays the way in and the standby. The link is built in three parts. Only the app part changes what a user sees.

- **The packet layer is the first part** (`server/src/link/packet.zig`, `Macterm/Link/LinkPacket.swift`). It has no cipher of ours: ChaCha20-Poly1305 from the Zig standard library and CryptoKit. A packet is `key_id u32`, `counter u64` (bit 63 is the direction), the sealed payload and the 16 byte tag. The nonce is 4 zero bytes and the counter. The 12 byte header is the associated data.
- **The roam rule:** `open` says if a counter is the newest. A caller may move the peer's address only on a packet that authenticates *and* is the newest. The replay window is 64 packets. It moves only after the tag is good.
- **A packet that does not authenticate gets no reply.** The two sides must make the same bytes: the vector in `packet.zig` is checked again in `LinkPacketTests`. `zig build fuzz-link --fuzz=…` fuzzes the parser, and CI runs it (`server.yml`).
- **The host part is the second part** (`server/src/link/host.zig`, `stream.zig`, protocol level 3). `link.open {secret, key_id}` makes the server open a UDP port (first free of `MACTERM_LINK_PORTS`, default 60001-60999) and answers `{port}`. The client makes the 32 byte key and sends it in this one request, over ssh. A result and an event never hold a secret, so the host cannot send it back. `MACTERM_LINK=off` in the server's environment turns the link off (`unavailable`). `link.close {key_id}`, 60 s with no authenticated packet at the start, and 24 h of silence end a link. `link.close` works from any connection, and a full table ends the link that heard last. The end of the opening ssh connection does not end it: the link must outlive ssh, which is the case that roaming serves. A link sends nothing after 30 s of silence (`quiet_ms`) and sends again after its next authenticated packet. A key that equals another link's key is refused, because the nonce is the counter alone. The client must make a new key for each `link.open`: the host cannot see a key reused after a restart, and a reused key repeats nonces. A bad `MACTERM_LINK_PORTS` turns the link off. The socket closes with the last link. A link's client must say `hello` within 5 s, like any client. The server's hello lists the cap `udp-link`.
- **A link is an ordinary client of the server.** The host joins UDP to one end of a socket pair and the server holds the other end as a peer (`addPeer` in `peers.zig`, through `Server.pending_peers`: a request cannot add to `peers` while the loop walks it). The relay, its skip-ahead and every request work on a link as on a socket. After a roam, the same peer and the same channels go on.
- **The stream under it is go-back-N** (`stream.zig`): DATA with an offset, cumulative ACK, a window of 32 KiB, a timeout that starts at 250 ms and doubles to 2 s, a keepalive ACK every 3 s. It is not R1 of design/009 (state, not bytes): the relay's skip-ahead already sends state, so the stream stays simple. `write` takes less when 256 KiB wait, and the host stops reading the socket pair.
- **Cost control:** a packet goes to the link that its `key_id` names. A source that is not the link's current client pays one token for its AEAD check (400 tokens, 200 a second). A packet that fails gets no reply.

## Session daemons and macOS attribution (#419)

macOS attributes work that needs privacy permission (Local Network, TCC) to the *responsible process* of a process. The value is fixed when the process starts, and the process inherits it from its parent.

- Because of this, the whole tree of a pane belonged to the Macterm that created its session. It belonged to nothing after that Macterm quit. Every process that survives becomes responsible for itself. A new start of Macterm that connects again over the zmx socket never attributes it again, because a connect is not a fork.
- From then on, macOS judged each pane program by its own identity. For anything that Apple did not sign, this meant `EHOSTUNREACH` on the local subnet, with no prompt.
- The fix: the server starts each session process with one `posix_spawn` that has `responsibility_spawnattrs_setdisclaim` (`spawnSession` in `registry.zig`). The session is its own responsible process from the first instant. Every program in the session belongs to **it** for the whole life of the session, whatever happens to the app.

- **The daemon has the signature of the app itself** (`scripts/embed-zmx.sh`). It uses the certificate of the app *and* the bundle identifier of the app. The certificate is the release certificate in CI, and it is ad-hoc on your Mac.
  - macOS identifies a responsible process by the identifier in its code signature. With the identifier of Macterm, the daemon resolves to the name of Macterm, its usage descriptions and its existing grants for Local Network and TCC. One grant covers the app and every pane.
  - Any other identifier names a second thing and needs a second grant. Examples: the `zmx` of the release download, which the linker signed, and a separate "Macterm Sessions". We tried the second one. The prompt only said "zmx", because a bare binary has no LaunchServices record that gives it a name.
  - Xcode never signs a Mach-O again when it copies it into `Resources/`. An ad-hoc daemon would be a new identity at every update.
  - `build.sh` refuses a release bundle whose zmx is ad-hoc or is not `com.thdxg.macterm`. `BundledResourcesTests` pins the identifier on the zmx of the built bundle. A change in a build phase therefore cannot turn every pane prompt into a prompt for "zmx" in silence.
- Full Disk Access follows the same attribution. The programs of the daemon satisfy the own TCC requirement of the app (identifier and certificate). They inherit its FDA grant, and this stays true after the first new start.
- You cannot change responsibility afterwards (`responsibility_set_*` needs a private entitlement). The disclaim exists only as a spawn attribute. This is why the server spawns `__session` itself, with no process between, and why there is no flag for it. The responsible root must *stay* a zmx process. A trampoline that ran the shell with exec would keep the pid, but the identity that macOS evaluates would become the identity of the shell.
- **One spawn starts a session.** The spawn has `POSIX_SPAWN_SETSID`, and on macOS `POSIX_SPAWN_CLOEXEC_DEFAULT`, so the session gets only the fds of the file actions: /dev/null on 0 to 2, and its end of a socket pair on `session.spec_fd`. On Linux every fd of the server is close-on-exec. The spec is one msgpack `SessionCreate.Args` on that socket pair. The session binds its socket, starts the shell, then answers `session.ready_answer` or its error text on the same fd (`session.run`). The session stays a child of the server until the server exits (`Server.children`). The `__create-session` verb asks the server, as `connect --` does.
- A session that an older build created keeps its old attribution until you create it again. The fix takes effect for each session.
- **An update removes the protected folders from each session that was open before it.** The update deletes the old bundle, so the session process has no file. tccd then cannot read its path (`proc_pidpath` fails with `ENOENT`). It denies Documents, Desktop and Downloads to the session and its programs.
  - A copy of the old bundle does not help: tccd uses the path that LaunchServices registered. An exec in place does not help: a running shell keeps its identity.
  - The app shows the Outdated pill on such a pane (`SessionBuild`). Its restart starts a new session from the new bundle.
  - Not marked: an old bundle that is moved and not deleted (for example to the Trash). The kernel still gives its path. Not measured: what tccd does then.
- To measure, use `responsibility_get_pid_responsible_for_pid` (a probe in C of ten lines). A Local Network prompt that nobody *answered* denies everything under that responsible process, also platform binaries. A subnet that looks dead can be a dialog that waits.
